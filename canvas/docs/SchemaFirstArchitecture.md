# DwoCanvas 스키마 중심 구조 설계

상태: 구현됨 (11장 구현 현황 참고) · 대상: DwoCanvas v0.2 · 관련 문서: `plugin/DwoCanvas/README.md`, `plugin/DwoCanvas/Schema/dwocanvas.schema.json`

## 1. 목적

DwoCanvas를 "Figma 플러그인 + UE 임포터"에서 **"정해진 시안 규격(JSON 스키마)을 받아 위젯 블루프린트를 만드는 플러그인"**으로 바꾼다.
Figma는 그 규격을 만들어 내는 여러 변환기(어댑터) 중 하나가 된다.

### 목표
- UE 플러그인은 시안이 어느 도구에서 왔는지 모른다. 규격만 안다.
- 새 시안 도구를 붙일 때 UE 코드를 고치지 않는다. 변환기만 새로 만든다.
- 규격을 지켰는지는 도구와 무관하게 같은 검증기와 같은 적합성 테스트로 판단한다.
- 기존 Figma 경로(v1 파일, 테스트 7개, Figma 왕복 검증)는 그대로 동작한다.

### 목표가 아닌 것
- 모든 도구의 모든 기능을 1:1로 옮기는 것. 규격에 없는 기능은 변환기가 굽거나(이미지) 버리고, 그 사실을 보고한다.
- 런타임 데이터 바인딩, 애니메이션, 인터랙션 자동 생성.

## 2. 현재 상태와 문제점

| 항목 | 현재 | 문제 |
|---|---|---|
| 중간 포맷 | `designbridge/1` JSON, `Schema/dwocanvas.schema.json` 존재 | 스키마가 **문서로만** 존재. 임포터는 느슨하게 읽고 검증하지 않음 |
| 역할 판단 | UE 임포터가 레이어 이름 접두사(`btn_`, `list_`, `$` …)로 판단. `meta.role`은 보조 | Figma 작업 방식이 UE 쪽 규칙에 박혀 있음. 이름 개념이 없는 원본(HTML 등)과 맞지 않음 |
| 글꼴 | `family` + `style` 문자열("SemiBold") | 스타일 이름이 도구마다 다름. 굵기를 이름에서 추정 |
| 이미지 | base64 내장 또는 상대 경로 `file` | 해시·URI 규약 없음. 큰 시안에서 JSON 비대 |
| 토큰 | 채우기의 `token` 이름 → `ColorTokenOverrides` | 색만 지원. 토큰 정의 자체는 파일에 없음 |
| 원본 정보 손실 | 표현 수단 없음 | 레이아웃 정보가 없는 원본(PSD)도 Figma와 같은 기대치로 경고 |
| 노드 ID | 재임포트의 기준인데 규약으로 명시돼 있지 않음 | 변환기가 매번 다른 ID를 주면 UE 작업이 보존되지 않음 |
| Lint | Figma 플러그인 안(`Figma/code.js`)에만 있음 | 다른 변환기 결과는 검사할 수 없음. CI에서 못 돌림 |
| 확장 | 컴포넌트 → 기존 클래스 연결(`ComponentOverrides`)만 | 프로젝트 고유 역할을 고유 위젯으로 만들 방법이 없음 |

## 3. 목표 구조

```
[시안 원본]   Figma   Photoshop   Penpot·Sketch   HTML/CSS   손으로 쓴 JSON   사내 툴
                 │         │            │             │           │
[변환기]     Adapters/Figma  Adapters/Psd  ...   Adapters/Html       (직접 작성)
                 └─────────┴────────────┴─────────────┴───────────┘
                                      ▼
[규격]        dwocanvas/2 JSON  ──  공용 검증기 (스키마 + 규칙)  ──  적합성 테스트
                                      ▼
[UE 플러그인]  버전 변환(v1→v2) → 스키마 검증 → 역할 처리기 → 위젯 트리 → 컴파일·저장
                                      → 재임포트 기록 · 리포트 · 시각 비교
```

### 책임 분리

| 계층 | 책임 | 원본 도구를 아는가 |
|---|---|---|
| 변환기 | 원본 읽기, 역할 결정(이름 규칙 등), 굽기 판단, 안정적 ID 부여, 미리보기 이미지 | 예 |
| 규격·검증기 | 형식 검증, 공통 규칙 검사(중복 이름, ID 누락, 지원 범위 밖 기능) | 아니오 |
| UE 플러그인 | 규격 → 위젯 변환, 재임포트 보존, 바인딩 검증, 시각 비교 | 아니오 |

## 4. 규격 v2 변경 사항

v2는 v1의 상위 집합이다. v1 파일은 임포터 안의 변환 단계가 v2로 올려서 처리한다(6장).

### 4.1 문서 머리

```json
{
  "schema": "dwocanvas/2",
  "source": { "tool": "figma", "adapter": "dwocanvas-figma/0.2.0", "file": "...", "exportedAt": "..." },
  "capabilities": ["layout.flow", "layout.constraints", "paint.gradient", "effects", "components", "variants", "tokens", "preview"],
  "tokens": { "$ref": "W3C Design Tokens 형식 (4.5)" },
  "assets": { "img_0": { "uri": "assets/img_0.png", "sha256": "...", "scale": 2 } },
  "documents": [], "components": [], "lint": [], "usage": {}
}
```

- **`capabilities`**: 원본이 제공한 정보의 종류. UE는 이 목록에 없는 정보에 대해 경고하지 않는다.
  - 예: PSD 변환기는 `layout.flow`를 넣지 않는다. 그러면 "자동 레이아웃이 없음" 경고가 사라지고, 절대 위치를 정상으로 받아들인다.
- **`source.adapter`**: 변환기 이름과 버전. 리포트와 재임포트 기록에 남겨 문제 추적에 쓴다.

### 4.2 노드: 역할을 정식 필드로

```json
{ "id": "12:34", "name": "btn_Apply", "type": "frame", "role": "button", "variable": true, "widgetName": "Apply", ... }
```

| 필드 | 의미 | 누가 채우나 |
|---|---|---|
| `role` | `button`, `list`, `tile`, `scroll`, `textInput`, `checkBox`, `slider`, `progressBar`, `switcher`, `namedSlot`, `spacer`, `ignore`, 또는 확장 역할 `x-<이름>` | 변환기 |
| `variable` | Blueprint 변수로 노출 여부 | 변환기 |
| `widgetName` | UE 위젯 이름(접두사 제거 등 정리된 이름). 없으면 `name`을 정리해서 사용 | 변환기 |

- v1의 `meta.role` / `meta.variable`은 v2의 정식 필드로 올라간다.
- UE의 접두사 규칙(`RoleRules`)은 **`role`이 비어 있을 때만 쓰는 예비 수단**으로 남긴다. 기존 v1 파일과 손으로 쓴 JSON을 위해서다.

### 4.3 텍스트

```json
"font": { "family": "Roboto", "weight": 600, "italic": false, "size": 16, "style": "SemiBold" }
```

- `weight`(100~900 숫자)와 `italic`이 정식 필드다. `style`은 참고용으로만 남긴다.
- UE 폰트 규칙도 굵기 숫자 → 서체(typeface) 매핑으로 바꾼다. 스타일 이름 추정은 예비 수단이 된다.

### 4.4 에셋

- `assets`(v1의 `images`)는 둘 중 하나를 쓴다.
  - `data`: base64 내장
  - `uri`: JSON 기준 상대 경로 또는 `file://` URI
- `sha256` 해시를 권장한다. UE는 이 값으로 중복을 제거하고, 같은 이미지는 다시 임포트하지 않는다.
- 변환기는 `scale`(배율)과 `nineSlice`를 함께 제공한다.

### 4.5 디자인 토큰

- 토큰 정의는 W3C Design Tokens Community Group 형식(`$value`, `$type`)으로 문서 머리의 `tokens`에 둔다.
- 노드는 값과 함께 참조를 적는다: `"color": [0.1,0.45,0.95,1], "colorToken": "color.primary"`.
- UE의 처리 순서: `ColorTokenOverrides`(프로젝트 덮어쓰기) → 문서의 토큰 정의 → 노드에 적힌 값.
- 우선 색 토큰부터 지원하고, 간격·반경·글꼴 토큰은 이후 단계로 둔다.

### 4.6 확장 영역

- 도구 고유 정보는 `x-<도구>` 키에 둔다. 예: `"x-figma": { "componentKey": "..." }`.
- UE는 모르는 `x-` 키를 무시하고 리포트에 정보로만 남긴다.
- 확장 역할(`role: "x-<이름>"`)은 7장의 처리기가 맡는다. 처리기가 없으면 일반 컨테이너로 만들고 경고한다.

## 5. 변환기 규약

변환기가 지켜야 할 조건이다. 공용 검증기가 확인한다.

1. **안정적인 ID (필수):** 원본이 바뀌어도 같은 요소에는 같은 `id`를 준다. 재임포트할 때 UE 작업을 보존하는 유일한 근거다.
   - Figma: 노드 id
   - Photoshop: 레이어 id
   - HTML: `data-db-id` 속성 (없으면 경고 후 DOM 경로 해시. 이 경우 재임포트 보존은 보장되지 않음)
2. **좌표와 단위:** `box`는 부모 기준 px, 회전 전 크기. 색은 sRGB 0~1.
3. **굽기 결정은 변환기 책임:** 규격이 표현하지 못하는 것은 변환기가 이미지로 굽고(`bake`), 무엇을 왜 구웠는지 `lint`에 남긴다.
4. **미리보기:** 시각 비교를 위해 각 문서의 렌더 이미지(`preview`)를 1배율로 제공한다. 제공할 수 없으면 `capabilities`에서 `preview`를 뺀다.
5. **이름 규칙은 변환기 쪽 설정:** 접두사 같은 팀 규칙은 변환기 설정 파일(예: `naming.json`)에 두고 역할로 바꿔서 내보낸다.

### 변환기 후보

| 원본 | 방식 | 제공 가능한 capabilities | 비고 |
|---|---|---|---|
| Figma | 현재 플러그인 이전 (`Adapters/Figma`) | 전부 | 기준 구현 |
| HTML/CSS | 헤드리스 브라우저로 계산된 레이아웃 추출. flex·grid → flow | `layout.flow`, `paint.gradient`, `effects`, `preview` | 성격이 가장 달라 **구조 검증용 두 번째 변환기로 권장** |
| Photoshop | `psd-tools`(MIT, Python)로 레이어 → 절대 위치 + 이미지 | `layout.constraints` 없음, `preview` | 레이아웃 정보가 거의 없음 |
| Penpot | 공개 포맷 / 플러그인 API | Figma와 유사 | 오픈소스 도구 |
| 손으로 쓴 JSON | 사람이 작성 | 작성자 재량 | 테스트·프로토타입용 |
| 이미지 · 텍스트 설명 · 낙서 | **추론형 변환기** (5.1) | `inferred` + 원본에 따라 `preview` | 정확한 추출이 아니라 검토용 초안 |

### 5.1 추론형 변환기

구조 정보가 없는 원본을 다룬다. 원본은 시안 캡처 이미지, 텍스트 설명, 그림판 낙서·와이어프레임이다.
규격 입장에서는 **다른 변환기와 똑같이 dwocanvas JSON을 내보내는 변환기 하나**다. UE 플러그인은 바꾸지 않는다.
다른 점은 결과가 "추출"이 아니라 "추정"이라는 것이다. 그래서 아래 규칙을 추가로 지킨다.

```
원본 (이미지 / 텍스트 / 낙서)
   ▼
1. 분석   OCR(글자 내용·위치) · 색 추출 · 영역 검출 · 비전·언어 모델(역할·레이아웃 추정)
   ▼
2. 생성   모델이 스키마에 맞춰 JSON 작성 (스키마와 사내 디자인 토큰을 입력으로 제공)
   ▼
3. 검증   공용 검증기 통과 필수. 실패하면 오류를 모델에 돌려주고 다시 생성 (최대 N회)
   ▼
4. 비교   (이미지 원본만) 원본을 preview로 써서 UE 렌더와 시각 비교 → 차이가 큰 영역만 다시 추론
   ▼
dwocanvas JSON 초안 + 확신도 리포트
```

| 원본 | 얻는 것 | 채우지 못하는 것 (기본값·토큰으로 대체) |
|---|---|---|
| 시안 이미지 | 위치·크기, 색, 글자(OCR), 역할 추정, 아이콘·일러스트는 잘라낸 이미지(`bake`) | 반응형 의도(Fill/Hug, 앵커), 컴포넌트 구분, 상태(Hover 등) |
| 텍스트 설명 | 화면 구조, 역할, 라벨 텍스트 | 모양 전부 (디자인 토큰·기본 스타일 사용) |
| 낙서·와이어프레임 | 영역 배치, 역할, 손글씨 라벨(OCR) | 정확한 크기·모양 (기본 스타일) |

**추가 규칙**
1. **출처 표시:** `capabilities`에 `inferred`를 넣는다. 추정으로 채운 값이 있는 노드에는 `confidence`(0~1)와 `inferred`(추정한 필드 목록)를 붙인다. 리포트는 확신도가 낮은 노드를 검토 대상으로 먼저 보여준다.
2. **ID와 재임포트:** 이미지에는 안정적인 ID가 없다. 추론형 결과는 **처음 생성용**으로 표시하고(`source.mode: "draft"`), UE는 재임포트 보존을 약속하지 않는다고 리포트에 적는다.
   - 권장 흐름은 초안을 **Figma로 불러와서(역방향 가져오기)** 다듬는 것이다. 그 뒤로는 기존 Figma 흐름을 탄다. 안정 ID, 재임포트 보존, 시각 비교가 모두 적용된다.
   - Figma를 거치지 않으면 UE에서 직접 다듬는다. 이 경우 같은 원본을 다시 넣어도 이전 결과를 덮어쓰지 않도록 새 WBP로 만든다.
3. **사내 디자인 시스템 우선:** 색·간격·글꼴은 원본에서 추정한 값보다 사내 토큰의 가장 가까운 값으로 맞추는 것을 기본으로 한다(설정으로 끌 수 있음). 이렇게 해야 결과가 프로젝트 스타일과 어긋나지 않는다.
4. **역할 추정 범위:** 기본 역할(button, list, scroll, textInput 등)만 추정한다. 확장 역할(`x-`)은 사람이 지정한다.
5. **결정성:** 같은 입력에 같은 결과가 나오도록 모델 설정(온도 등)과 프롬프트·모델 버전을 `source.adapter`에 기록한다.

**구성 요소**

| 구성 | 역할 | 비고 |
|---|---|---|
| `Adapters/Inference/` | 파이프라인 (Python CLI) | 공용 검증기와 같은 언어 |
| OCR | 글자 내용·위치·크기 | 사내 실행 가능한 오픈소스 우선. 라이선스 검토 필요 |
| 비전·언어 모델 | 역할·레이아웃 추정, JSON 생성 | 외부 API 또는 사내 모델 (10장 결정 사항) |
| 이미지 잘라내기 | 아이콘·일러스트 → `bake` 이미지 | 원본 이미지에서 영역 추출 |
| 역방향 가져오기 | dwocanvas JSON → Figma 문서 | Figma 변환기에 "가져오기" 기능 추가 |

**검증 방법**
- 적합성 테스트에 "추론형" 케이스 묶음을 따로 둔다. 예: 기존 DWO 시안의 Figma 미리보기 이미지를 원본으로 넣는다.
- 기준은 두 가지다.
  - **구조 일치율:** Figma에서 추출한 정답 JSON과 비교해, 역할과 계층이 얼마나 맞는지
  - **시각 차이:** 원본 이미지와의 픽셀 차이
- 추출형처럼 0.x%를 목표로 하지 않는다. 단계별 목표치는 첫 측정 후에 정한다.

## 6. UE 플러그인 변경

| 영역 | 변경 |
|---|---|
| 가져오기 첫 단계 | **스키마 검증**을 추가한다. 위반은 노드 경로와 함께 오류로 보고하고 가져오기를 중단한다(설정으로 "경고만" 선택 가능) |
| 버전 변환 | `v1 → v2` 변환기를 둔다: `images`→`assets`, `meta.role`→`role`, 스타일 이름 → `weight` 추정 |
| 역할 결정 | `role` 필드 우선, 없을 때만 `RoleRules` 접두사 |
| capabilities | 목록에 없는 정보에 대한 경고를 끈다 |
| 재임포트 기록 | `source.adapter`를 기록. 변환기가 바뀌면 리포트에 알림 |
| 폴더 정리 | `Figma/` → `Adapters/Figma/`. 검증기는 `Tools/Validator/` |

## 7. 확장 지점: 역할 처리기

프로젝트가 자기 위젯을 연결할 수 있도록 C++ 인터페이스를 연다.

```cpp
class IDwoCanvasRoleHandler
{
public:
	virtual ~IDwoCanvasRoleHandler() = default;
	/** 이 처리기가 맡는 역할 이름 (예: "button", "x-inventorySlot"). */
	virtual FName GetRole() const = 0;
	/** 노드에 해당하는 위젯을 만든다. 자식 처리 여부는 OutBuildChildren으로 알린다. */
	virtual UWidget* Build(FDwoCanvasBuildContext& Context, const FDwoCanvasNode& Node, bool& bOutBuildChildren) = 0;
};

// 모듈 시작 시 등록
FDwoCanvasEditorModule::Get().RegisterRoleHandler(MakeShared<FMyInventorySlotHandler>());
```

- 기본 역할(`button`, `list` …)도 같은 인터페이스로 구현한다. 그러면 프로젝트가 기본 처리기를 바꿔 끼울 수 있다. 예: 버튼을 CommonUI 버튼으로.
- 지금의 `ComponentOverrides`는 "컴포넌트 이름 → 클래스"만 지원한다. 이것을 "역할 또는 컴포넌트 → 처리기"로 일반화한 것이다.
- 처리기 안에서도 재임포트 기록(`Make`), 슬롯 복원, 변수 설정은 공용 컨텍스트를 통해 쓴다. 그래야 보존 규칙이 깨지지 않는다.

## 8. 공용 검증기와 적합성 테스트

### 검증기 (`Tools/Validator`)
- 형태: 단독 실행 CLI(Python). UE 없이 돌아간다.
- 검사 항목
  - JSON 스키마 검증
  - 같은 부모 아래 `widgetName` 중복
  - `id` 누락이나 중복
  - `capabilities`와 실제 내용 불일치
  - 굽기 이미지 누락
  - 역할별 필수 조건 (예: `list`의 첫 자식은 컴포넌트 인스턴스)
- 출력: `lint` 형식 JSON. 변환기가 내보내기 전에 호출하고, CI에서도 돌린다.
- Figma 플러그인 안의 Lint 규칙 중 도구와 무관한 것은 검증기로 옮긴다.

### 적합성 테스트 (`Conformance/`)
- 기능별로 `case.json`과 `expected.png`를 한 쌍씩 둔다. 예: 가로 쌓기 + 간격, 그라데이션, 테두리 정렬, 텍스트 줄바꿈, 앵커, 굽기 overflow 등.
- UE 자동화 테스트가 각 케이스를 가져와 렌더하고, 기대 이미지와 비교한다. 지금의 Fidelity 테스트를 일반화한 것이다.
- 새 변환기는 "같은 시안 → 같은 JSON 의미"를 보이기 위해, 자기 원본으로 만든 케이스를 이 목록에 추가한다.

## 9. 진행 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1. 규격 v2 | 스키마 v2, v1→v2 변환, 가져오기 전 스키마 검증, 규격 문서 | 기존 테스트 7개와 Figma 왕복(시각 비교 0.5% / 0.9%) 유지. v1·v2 파일 모두 가져와짐 |
| 2. 구조 정리 | `role` 필드 우선, 접두사 규칙을 Figma 변환기 설정으로 이동, `Adapters/` 폴더, 공용 검증기 | Figma 변환기가 v2를 내보냄. 검증기가 CLI로 동작 |
| 3. 두 번째 변환기 | HTML/CSS 변환기(권장) 또는 PSD 변환기 | 같은 화면을 두 원본으로 만들었을 때 UE 결과의 시각 비교가 기준 이내 |
| 4. 처리기 등록 | `IDwoCanvasRoleHandler`, 기본 역할을 처리기로 이전 | 프로젝트 모듈이 확장 역할 하나를 등록해 사용하는 테스트 통과 |
| 5. 토큰 확장 | 간격·반경·글꼴 토큰, 테마 전환 | 토큰 값만 바꿔 재임포트했을 때 해당 속성만 바뀜 |
| 6. 추론형 변환기 | 5.1의 파이프라인, `confidence`·`inferred`·`source.mode` 규격 추가, Figma 역방향 가져오기 | DWO 시안 이미지 → 초안 JSON이 검증을 통과하고 UE로 가져와짐. 구조 일치율·시각 차이를 측정해 기록 |

- 6단계는 1·2단계(규격 v2, 공용 검증기)와 5단계(토큰)에 의존한다. 검증기와 토큰이 있어야 추론 결과를 걸러내고 스타일을 맞출 수 있기 때문이다.
- 3단계(두 번째 추출형 변환기)보다 먼저 할 수도 있다. 단, "도구 중립 구조"의 검증은 추출형 변환기로 하는 편이 정확하다.

## 10. 위험과 결정할 사항

| 항목 | 내용 | 제안 |
|---|---|---|
| v1 호환 기간 | v1 지원을 언제까지 유지할지 | v2 안정화 후 한 번의 마이너 버전 동안 유지 |
| 스키마 위반 처리 | 엄격 중단 vs 경고 후 진행 | 기본은 중단, 설정으로 완화 |
| 안정적 ID가 없는 원본 | HTML 등에서 ID를 못 받는 경우 | 첫 생성 전용으로 표시하고, 재임포트 보존을 보장하지 않는다고 리포트 |
| 검증기 언어 | Python vs Node | Python (UE 에디터 Python과 공유 가능, `jsonschema` 라이브러리는 MIT) |
| 라이선스 | 변환기가 쓰는 외부 라이브러리 | 도입 전 라이선스 검토 (예: `psd-tools` MIT) |
| 글꼴 측정 차이 | 도구마다 글자 렌더링이 달라 텍스트 영역의 차이는 남음 | 적합성 기준을 "글자 외 영역 기준"과 "전체 기준"으로 나눔 |
| 추론에 쓸 모델 | 시안 이미지를 외부 AI API로 보내도 되는가 (보안·계약) | 사내 정책 결정이 먼저. 외부 전송이 안 되면 사내 실행 모델 + OCR로 가고 정확도 목표를 낮춤 |
| 추론 결과의 책임 | 초안이 그럴듯해 보여 검토 없이 쓰일 위험 | `source.mode: "draft"`와 낮은 확신도 노드를 리포트 맨 앞에 표시. 초안 WBP는 별도 폴더에 생성 |
| 추론 비용·시간 | 화면마다 모델 호출과 재시도 비용 | 재시도 횟수 상한, 결과 캐시(입력 해시 기준) |
