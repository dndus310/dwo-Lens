01 · Overview

한눈에 보기

03 · Principles

설계 원칙

모든 공정과 도구는 아래 네 가지를 지킵니다. 새 도구를 추가할 때도 이 기준으로 판단합니다.

P1 · 무결합

언제 떼어 내도 프로젝트는 그대로

모든 공정은 A 프로젝트를 읽기만 합니다. 시스템 파일은 .git/info/exclude로 이력에 잡히지 않고, .uproject는 건드리지 않습니다. 패키지를 수정하는 엔진 도구(ResavePackages 등)는 실행하지 않습니다.

P2 · 결정적 우선

도구가 먼저, AI는 마지막

사실은 도구가 추출하고 UE 규칙으로 확정합니다. 검증 게이트를 통과한 결과 중 도구로 확정할 수 없는 것만 AI가 해석합니다.

P3 · 산출물 계약

공정 간 전달은 JSON으로만

각 공정의 입출력은 버전이 있는 스키마(assay.raw, assay.graph, assay.logs 등)로 정합니다.

P4 · 실행 기록

모든 결론을 추적하고 재현

실행마다 run.json에 실행 ID, 공정별 판정과 소요 시간, 시스템 커밋을 남깁니다.

04 · Attach

프로젝트 부착

PC마다 setup.bat을 한 번 실행해 DWO_ASSAY_HOME을 등록합니다. 그다음 __dwo-assay.bat 하나를 대상 프로젝트 루트에 복사해 실행합니다. 시스템 본체는 git clone으로 들어가므로 버전 확인, 업데이트, 제거를 git이 맡습니다.

STEP 1사전 확인

.uproject, 프로젝트 자체 git 저장소 여부, git, DWO_ASSAY_HOME

STEP 2exclude 등록

파일을 만들기 전에 표식 블록을 먼저 기록합니다

STEP 3clone 또는 pull

시스템 저장소를 __dwo-assay/system으로 가져옵니다

STEP 4플러그인 설치

엔진 버전별로 캐시된 바이너리 복사, state.json, doctor

A 프로젝트 안의 구조

A/
├─ __dwo-assay.bat              # 제어 진입점
├─ __dwo-assay/
│  ├─ system/                   # 시스템 clone
│  ├─ data/runs/<id>/           # raw · out · run.json
│  ├─ config.json               # (선택) 규칙 덮어쓰기
│  └─ state.json
└─ Plugins/__DwoAssayInspector  # 바이너리만, Source 없음

exclude 표식 블록

# 팀원이 직접 쓴 줄은 건드리지 않음
*.log

# >>> dwo-assay managed (do not edit) >>>
/__dwo-assay/
/__dwo-assay.bat
/Plugins/__DwoAssayInspector/
# <<< dwo-assay managed <<<

경로는 git rev-parse --path-format=absolute --git-path info/exclude로 구하므로 worktree에서도 동작합니다.

명령동작
attach / update사전 확인 → exclude → clone/pull → 플러그인 설치 → doctor. 다시 실행하면 업데이트로 동작합니다.
analyze아키텍처 리포트와 품질 점검
verifyBP 전체 컴파일, 데이터 검증, 자동화 테스트
logsSaved/Logs, Saved/Crashes 분석, 이전 실행 대비 새 오류 표시
tools / status / doctor도구 카탈로그, 부착 버전·업데이트 여부, 환경 점검
detach [--keep-data]플러그인·exclude 블록·작업 폴더 제거, git 상태 비교, batch 자기 삭제
주의 대상 프로젝트는 자체 git 저장소여야 합니다. 상위 폴더 저장소(예: 홈 폴더 전체가 저장소인 경우)에 포함되어 있으면 부착을 거부합니다. C++ 프로젝트는 에디터 바이너리가 빌드된 상태여야 하며, Build.cs·Target.cs에 시스템 관련 내용이 섞이지 않았는지는 커밋 전에 작업자가 확인합니다.
05 · Control panel

제어판 GUI

명령어 대신 창에서 같은 작업을 합니다. Dear ImGui와 DirectX 11로 만든 단독 실행 파일이라 에디터와 분리되어 있고, 내부적으로 __dwo-assay.bat을 그대로 실행하므로 명령줄과 결과가 같습니다.

09 · StateMonitor

StateMonitor 연계

StateMonitor는 프로젝트 코드가 USTRUCT 값을 제출하면 필드 트리, JSON, 변경 이력을 보여 주는 런타임 플러그인입니다. 프로젝트 코드가 호출해야 동작하므로 dwo-Assay가 주입하지 않고, 프로젝트가 이미 쓰고 있을 때만 연계합니다.

역할 분석

무엇을 하는 도구인가

UStateMonitorSubsystem::Submit(SourceId, Struct)로 받은 값을 복사해 트리·JSON·변경 이력으로 보관하고 Slate 뷰어로 보여 줍니다. 게임 인스턴스 서브시스템이라 레벨이 바뀌어도 이력이 남고, 자동화 테스트 StateMonitor.* 6개가 있습니다. 조사한 기성 도구 중 같은 일을 headless로 하는 것은 없었습니다.

연계 방식

어댑터가 하는 일

감지: 플러그인 존재·활성 여부, C++·BP 제출 지점과 Source ID를 statemonitor.json으로 기록. 검증: verify에 StateMonitor. 테스트를 자동 추가. 수집(계획): 실행 중 스냅샷을 JSONL로 내보내 같은 실행 ID의 로그·트레이스와 결합.

{
  "naming": { "forbidAssetsAtContentRoot": false },

  "verify": {
    "automationFilters": ["Project.", "MyGame."],
    "timeoutMinutes": 45
  },
  "logs": { "maxFiles": 20 }
}

확인 사항

완료한 항목은 채워진 상자, 남은 항목은 빈 상자입니다.

  • BP 하나를 JSON으로 덤프Commandlet이 5.7.4에서 동작, BP 2개·에셋 150개 추출
  • UE 내장 검증 명령 확인CompileAllBlueprints, DataValidation, Automation RunTests, -ReportExportPath를 5.7 소스와 실행으로 확인
  • 부착 · 제거 왕복 테스트BP 전용·C++ 프로젝트 모두 제거 후 git 상태 동일
  • C++ 프로젝트에서 사전 빌드 플러그인과 프로젝트 빌드의 공존 확인Source 없는 플러그인이 프로젝트 빌드(UBT)에 영향을 주지 않는지 실제 빌드로 확인
  • Clang 파싱 실패율 측정C++ 호출 그래프(Phase 2) 착수 전, 대상 프로젝트로 컴파일 DB 생성 후 시범 파싱
  • Gauntlet 테스트 노드 이름, memreport·LLM 플래그, 크래시 폴더 형식리서치에서 확인 필요로 남은 항목
